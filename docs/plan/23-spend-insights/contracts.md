## 1. Classification core

Frozen: the taxonomy, the labelling rules, the `Decider` interface and **one** pipeline entry point. Nothing else in `src/insights/*` is frozen.

**`work` (2.36, CAT1): spending on the customer's own work or projects.** It is spending: it counts in every total like any other spend category; it is neither savings nor a transfer. It holds: the self-employed social-security quota (cuota de autónomos: TGSS, Seguridad Social RETA), professional software licences and tools (GitHub, JetBrains, Adobe, Figma, Notion, Atlassian, Microsoft 365 Business), domains and hosting (Hetzner, DigitalOcean, OVH, GoDaddy, AWS), coworking, professional courses and certifications (Udemy, Coursera, Platzi), and payments for one's own projects when the merchant says so unambiguously. It does not hold: everyday subscriptions (Spotify, Netflix, Disney+ stay `eating_out_leisure`), general shopping (Amazon stays where it is), phone and internet (`home_utilities`). A merchant that can be personal or professional (Apple, Google, a Microsoft charge without "Business") is not `work` by rule: a wrong "Work" label is worse than a movement left to sort. Which merchants the rules know is not frozen (§1 Rules). A rule the customer makes for this category from the chat still needs their explicit yes, as for any category.

### Labelling rules (final)

These decide what the rules produce and what the labelled sets expect. First match wins.

1. **Own account wins, in both directions.** A movement whose counterparty is one of the customer's own accounts is `savings_internal`, debit or credit, whatever the concept says. "Own" is known from any of: the app's own record of the operation (`fromAccountId` and `toAccountId` both own), two legs of one `operationId` on the customer's accounts in the same bank answer (the detection `activityRows` in `src/ui-helpers.ts` already uses for "Between your accounts"), or a description that names an own account id.
2. **A person transfer stays a person transfer, whatever its concept.** A debit to a non-own account known from the app's record, or whose description is a transfer to a person (the banks' transfer wording, Bizum sent, "transferencia a favor de"), is `transfer_person`. The purpose words in its concept become **candidates** (`p: null`), never the category; the concept is `MovementInput.concept` when the app has a record, otherwise the text after the bank's transfer wording in the description. The matching credit on the receiving side is `income` (reason `credit`).
3. **Opening rows** (`Opening balance`, `Initial deposit`, `Savings account opening`) are `other`, and are excluded from income totals.
4. **The customer's own rule** for the merchant key. It is reached only by a movement that rules 1–3 do not decide, so a rule never changes a transfer or an opening row, and none is made from one (§3: such a movement is set by hand, alone).
5. **Credits.** A refund from a merchant a rule recognises takes that merchant's purchase category. A tax refund is `other`. A refund from an unrecognised merchant is `other`. A credit whose leading words name a transfer between own accounts or savings (e.g. `TRASPASO ENTRE CUENTAS PROPIAS`) gets **no rule decision** unless an account fact of rule 1 says the counterparty is own: wording alone never gives `savings_internal`, and such a credit is not counted as income either. Any other credit is `income`, as an estimate.
6. **Debits: the regex dictionary**, priority overrides first, then general entries. Exactly one category matched → that category. Two or more → no rule decision. In rules 5 and 6 only the **merchant part** of a description can decide: its leading words, before any free text (a concept, a reference, a note, an instruction). A brand or an institution decides anywhere in the merchant part; a generic word (`FARMACIA`, `TAXI`, `GROCERIES`) only as the first word of the merchant name. Text after the merchant part never selects a category; it can only give candidates. A debit whose leading words are transfer or own-money wording, with no account fact (rules 1 and 2) and no person wording of rule 2, gets no rule decision, whatever its concept says.
7. Otherwise the decider, then the threshold.

A debit can never be `income`. `other` decided by a rule (cash, fees, taxes, fines, opening rows) is state `estimated`, not `needs_review`: the customer is not asked about every cash withdrawal.

### Pipeline entry point (`src/insights/classify.ts`)

```ts
export type MovementInput = {
  id: string; accountId: string; amountCents: number; description: string; createdAt: string;
  operationId?: string | null; fromAccountId?: string; toAccountId?: string; concept?: string;
};
export type Candidate = { category: CategoryId; p: number | null }; // p null: suggested by a rule
export type RowCategory = {
  id: CategoryId;
  state: 'estimated' | 'confirmed' | 'needs_review' | 'pending';
  source: 'user' | 'user_rule' | 'rule' | 'model' | 'none';
  reason: string; // see "Reasons"
  confidence: number | null; // 0..1, model decisions only
  threshold: number | null; // the bar in force for that decision
  candidates: Candidate[]; // at most 3, best first
  merchantKey: string;
  model: string | null; // e.g. 'systemone:jev-1.13.0'
};
export function classifyMovements(input: {
  userId: string;
  movements: MovementInput[]; // one bank answer
  ownAccountIds: ReadonlySet<string>;
  deciders?: Decider[]; // default: the chain from the environment
  wait?: boolean; // default false
  profile?: boolean; // default true; see "Merchant profile"
}): Promise<Map<string, RowCategory>>; // key: movement id; one entry per input movement
```

Observable behaviour:

- With `wait: false` it resolves without waiting for any decider: stored decisions and rule decisions are returned; a movement still to be decided is `{id: 'other', state: 'pending', source: 'none', reason: 'pending'}`. The decider work continues in the background, one run per customer at a time.
- With `wait: true` it resolves when that background work for this customer has finished; no entry is `pending`.
- Decisions are stored per customer and movement. A second call with the same movements calls no decider.
- One decider call per distinct **merchant key and sign** in a call; movements sharing them get the same decision.
- A movement with an empty merchant key, or with a **generic** one (channel words only, see "Merchant key"), is never sent to a decider: `other` · `needs_review` · reason `no_merchant`. The customer's rule for a generic key (rule 4) still applies, before this.
- With an empty chain: `other` · `needs_review` · source `none` · reason `no_decider`, at once.
- Model answer: `confidence ≥ threshold` and the top option is not `other` → that category · `estimated` · source `model`. Otherwise `other` · `needs_review` · source `model` · reason `below_threshold`, with the candidates kept.
- **Decider failure never leaves a movement pending.** When every decider in the chain has failed for an item (attempt budget in §6), it is stored `other` · `needs_review` · source `none` · reason `decider_unavailable`. Such a row is sent to a decider again only by an explicit refresh (`POST /api/insights/reclassify`) or when it is more than 24 hours old.
- A model answer whose top option the sign rule forbids for that movement (a credit answered `transfer_person`) is treated as below the threshold: `other` · `needs_review` · reason `below_threshold`, with the allowed candidates kept.
- A `confirmed` row is never overwritten by a rule or a model.
- A stored row whose movement content changed under the same id (other amount, date, description or account) is ignored and replaced.
- A failure of the store does not throw: every movement comes back `pending`.
- `RowCategory.model` of a model decision is `<decider.id>:<Decision.model>`, whatever the decider (the pipeline adds the prefix): `systemone:jev-1.13.0`, `openai:<model>`.
- The pipeline calls `classify` **once per item and decider**. The attempt budget of §6 is spent inside an adapter, so a `Decider` that throws is not called again for that item: the item goes to the next decider, or is stored `decider_unavailable`.
- A stored `no_decider` row is classified again by the first call that has a decider (a customer first seen without a key is not left unclassified once there is one).
- **Daily budget (IT4).** One customer's movements send at most `DECIDER_DAILY_ITEMS` items (merchant key and sign) to a decider per rolling 24 hours, counted in the database (table `decider_asks`, §2), whatever the answer was: a failed item counts. Budget is taken for a whole run before its first request. An item that gets none is stored `other` · `needs_review` · source `none` · reason `decider_budget` (never pending), with the rule candidates; it is sent by the first call that finds room in the rolling day, with no action by the customer.
- **An answered movement is not asked again (IT4).** A decider's answer is kept with the movements it was given for (by content: account, amount, date, description). When the row of such a movement is gone (its rule was deleted, the row was deleted) the kept answer is its decision again, inside the call, with no decider request and no budget, as long as the chain is the same deciders and model ids (`DECIDER`, `DECIDER_MODEL`, `OPENAI_CHAT_MODEL`). A movement no decider answered (a new movement of a known merchant, a failed item) is sent as before.
- A movement that goes to review with no model candidate carries what the rules can suggest: at most three candidates with `p: null`, each allowed by the sign rule; none for the guaranteed unknown.
- `classifyMovements(input, now?)` takes an optional second argument, `now: () => Date`, for tests: the clock of the 24-hour rule and of the stored `updatedAt`.

**Merchant key** (`RowCategory.merchantKey`): matches `/^[A-Z0-9& ]{0,40}$/`, no leading, trailing or double space. When the description has no letter left after cleaning, the key is the **channel words** that were stripped from its start (a **generic key**: `Card payment 12` → `CARD PAYMENT`, `Purchase 1234` → `PURCHASE`, `TPV 0041` → `TPV`, `Recibo 2291` → `RECIBO`, `COMPRA TARJ. 4532XXXX 0098231 ES` → `COMPRA TARJ`), and `''` when there were none (`1234567`, `27/09 03:41`) or only a payment processor (`PAYPAL *JGARCIA88`: the payees behind a processor differ, and one rule on `PAYPAL` would label them all). The channel words are `COMPRA TARJ`, `COMPRA EN`, `PAGO EN`, `PAGO CON TARJETA`, `CARD PAYMENT`, `PURCHASE`, `TPV`, `ADEUDO RECIBO`, `ADEUDO SEPA`, `RECIBO`; `genericKey(key)` in `src/insights/normalize.ts` says whether a key is one of them. Movements with a generic key form one review group and can take the customer's rule; the key is never sent to a decider and matches no dictionary entry. Fixed examples: `COMPRA TARJ. 4532XXXXXXXX1234 MERCADONA 0412 VALENCIA ES` → `MERCADONA`; `PAYPAL *SPOTIFY 35314369001` → `SPOTIFY`; `SUMUP *ESPAI NOU` → `ESPAI NOU`; `ZARA ESPANA S.A. 3321 MADRID` → `ZARA ESPANA`; `100 MONTADITOS 0456 SEVILLA` → `100 MONTADITOS`. The same merchant written with different card masks (`4532XXXXXXXX1234`, `XXXX XXXX XXXX 1234`, `TARJ. *1234`), dates (`12/09`, `12-09-2026`, `12SEP`), times (`21:45`) and terminal ids gives the same key.

**Cleaned description** (`DecisionItem.description`, the only text of a movement a decider is sent): the description without the banks' transfer wrapper, upper case, no accents, only `[A-Z0-9& ]`, and without any **reference token**: a token of four or more characters that holds a digit (a card mask in any form and its last four digits — `****1234`, `XXXX XXXX XXXX 1234`, `4532XXXXXXXX0098`, `**** 0098` —, a terminal id, a reference, any run of four or more digits) or a run of four or more `X`. These are the tokens the merchant key drops. At most 80 characters. `AMZN MKTP ES 7HH21MM04` → `AMZN MKTP ES`; `TRANSFERENCIA 000123` → `TRANSFERENCIA`; `COMPRA TARJ. 4532XXXXXXXX1234 MERCADONA 0412 VALENCIA ES` → `COMPRA TARJ MERCADONA VALENCIA ES`. A lone short number stays (`100 MONTADITOS`, `FARMACIA 24H`). **Runs of digit-only tokens (IT7, 2.22):** a digit-only token next to another digit-only token is dropped too: a phone number written in groups or a date, never a name (`BIZUM ANA 600 123 456` → `BIZUM ANA`; `COMPRA EN DIA % S.A. 08-09 TARJ *7781` → `COMPRA EN DIA S A TARJ`). This is about the text a decider is sent only: the rules and the merchant key read the description itself. Sending the merchant key instead of the cleaned description is a possible stricter option, not taken: its effect on accuracy is not measured.

**Reasons** (`RowCategory.reason`, stored): `own_account`, `person_transfer`, `opening_balance`, `user`, `user_rule:<merchant key>`, `keyword:<matched text>`, `refund:<matched text>`, `tax_refund`, `credit`, `model`, `below_threshold`, `named_in_text`, `decider_unavailable`, `decider_budget`, `no_decider`, `no_merchant`, `pending`.

| Reason | Given by |
|---|---|
| `own_account` | labelling rule 1 (`savings_internal`) |
| `person_transfer` | rule 2, the debit (`transfer_person`) |
| `credit` | rule 2, the receiving credit, and rule 5 "any other credit" (`income`) |
| `opening_balance` | rule 3 (`other`) |
| `user_rule:<merchant key>` | rule 4 (state `confirmed`, source `user_rule`) |
| `refund:<matched text>`, `tax_refund` | rule 5 |
| `keyword:<matched text>` | rule 6 |
| `model`, or `model:<time>,<day>` with the profile labels that are not `mixed` | a model answer that is shown |
| `below_threshold`, `named_in_text`, `decider_unavailable`, `decider_budget`, `no_decider`, `no_merchant` | review, as in "Observable behaviour" (`named_in_text`, 2.29: a model answer above the bar that is the category the description itself names; `decider_budget`: the customer's daily decider budget was used up; it clears by itself) |
| `user` | set by hand (SI5) |

A fixed refund example for tests: the credit `DEVOLUCION COMPRA MERCADONA 0412 VALENCIA ES` is `groceries` · `estimated` · `refund:…`. Other refund words and the merchants the dictionary knows are not frozen.

**Guaranteed unknown:** a description of the form `ZZQXV` followed by a space and letters (for example `ZZQXV ALPHA`) matches no global rule, now or later. Tests use it to get a movement that reaches the decider. It blocks only the global rules (5 and 6, and the person wording of rule 2), on either sign: the account facts of rules 1 and 2, the banks' transfer wrapper and the customer's own rule (rule 4) still apply, and an unknown `ZZQXV …` credit is not `income` (it goes to the decider, or to review).

**Simulator descriptions:** `September salary` → `income`; `Opening balance` → `other`; `Groceries` → `groceries`; `Internet bill` → `home_utilities`; `Coffee shop` → `eating_out_leisure`; `Transport` → `transport`; all `estimated`, source `rule`. The seed row `Transfer to external savings` is not in this list: it is transfer wording with no account fact, so no rule decides it (with `DECIDER=none` it is `other` · `needs_review` · `no_decider`).

### Decider interface (`src/insights/decider.ts`)

```ts
export type DecisionItem = {
  key: string; // merchant key + sign; opaque to the decider
  description: string; // cleaned description: upper case, no accents, [A-Z0-9& ], no reference token, no run of digit-only tokens, at most 80 chars
  direction: 'debit' | 'credit';
  profile: MerchantProfile; // labels only, never raw numbers, times or dates
};
// Computed over this merchant's movements (same merchant key and sign) in the current bank answer.
export type MerchantProfile = {
  typical_time: 'late_night' | 'morning' | 'midday' | 'evening' | 'mixed';
  typical_day: 'weekday' | 'weekend' | 'mixed';
  typical_amount: 'small' | 'medium' | 'large' | 'mixed';
  occurrences: 'once' | 'few' | 'recurring_monthly' | 'frequent';
};
export type Decision = {
  candidates: Candidate[]; // p set; best first; categories from DECIDER_OPTIONS only
  confidence: number; // 0..1; what the threshold is compared with
  model: string; // the model id the provider reported
};
export interface Decider {
  id: 'systemone' | 'openai';
  threshold: number; // 0..1, the bar for this decider
  classify(item: DecisionItem): Promise<Decision>; // one movement per call; throws DeciderError
}
export class DeciderError extends Error {
  constructor(retryable: boolean, status?: number, retryAfterS?: number);
  retryable: boolean; status?: number; retryAfterS?: number;
}
export function deciderChain(): Decider[]; // from the environment (§5)
```

**Merchant profile.** Time and amount are decision inputs, as labels, and there is still one decision per merchant key and sign. Buckets, in `Europe/Madrid`:

| Label | Buckets |
|---|---|
| time | `late_night` 00:00–05:59 · `morning` 06:00–11:59 · `midday` 12:00–16:59 · `evening` 17:00–23:59 |
| day | `weekend` Saturday, Sunday · `weekday` otherwise |
| amount (on `\|amountCents\|`) | `small` < 1500 ≤ `medium` < 10000 ≤ `large` |

`typical_time`, `typical_day`, `typical_amount`: the bucket that holds at least two thirds of the merchant's movements, else `mixed`; with one movement, its bucket. `occurrences`: `once` for 1 movement; `recurring_monthly` for 2 or more movements in different calendar months with at most one per month; `frequent` for 4 or more otherwise; `few` otherwise. Example: three movements of `LA ESQUINA` at 01:30, 02:10 and 00:45 on weekend nights, 14–21 EUR → `{late_night, weekend, medium, few}`. The profile is computed when the decision is made; a stored decision is not recomputed when the window changes. A stored model decision's `reason` may cite it (`model:late_night,weekend`; the reason still starts with `model`).

`classifyMovements` accepts `profile?: boolean` (default `true`); with `false` every label is sent as `mixed` and `occurrences` as `once` (used by the evaluation's ablation).

Two error classes only: **retryable** (429, 5xx including 529, 408, timeout, network) and **not retryable** (401, 422, any other 4xx).

## 3. HTTP

```ts
  // The ids to send when changing this row: one id, or both legs of a merged "Between your accounts" row.
  movementIds: string[];
};
type SpendingSummary = {
  range: { from: string | null; to: string | null };
  window: { returned: number; oldestAt: string | null; mayBeTruncated: boolean };
  partial: boolean; // a requested `from` is earlier than window.oldestAt
  spentCents: number; // sum of categories[].spentCents
  incomeCents: number; // credits whose category is `income`
  categories: {
    id: CategoryId; label: string; // English
    spentCents: number; // |debits| minus refund credits in this category
    count: number;
    confirmedCents: number; estimatedCents: number; // sum = spentCents
  }[]; // spend categories and `other`; count > 0; largest spentCents first
  unresolved: {
    count: number; totalCents: number;
    groups: { merchantKey: string; title: string; count: number; totalCents: number;
              movementIds: string[]; candidates: Candidate[]; reason: string;
              direction?: 'debit' | 'credit' }[]; // largest totalCents first; `direction` since 2.16
  };
  pending: number;
  decider: 'systemone' | 'openai' | 'none';
};
type SetCategoryResult = {
  updated: number; // movements changed, including similar ones
  similar: { merchantKey: string; count: number; movementIds: string[] }[];
  rules: string[]; // merchant keys that have a rule after this call
};
```

Totals:

- Spend = debits whose category is neither `savings_internal` nor `income`, minus credits (refunds) in a spend category. `transfer_person` and `other` count as spend categories.
- Income = credits whose category is `income`. Credits in `other` (opening rows, tax refunds) and everything in `savings_internal` are in no total.
- `unresolved` = movements in state `needs_review`. One group per **merchant key and sign** (as the pipeline decides them), so two groups can carry the same `merchantKey`, one of debits and one of credits, and a group can always be set whole; a movement with an empty merchant key is its own group. A movement in review has category `other`, so a debit in review is also counted in the `other` category (in `spentCents` and `estimatedCents`); it is in no named category.
- A `pending` movement is in no total and no group; it is only counted in `pending`.
- `decider` is the first decider of the environment chain, or `none`.

Periods (since 2.17, IT8; `periodSummary` and `parsePeriod` in `src/insights/summary.ts`):

```ts
type PeriodSummary = SpendingSummary & {
  // the one applied: 'all', 'YYYY-MM', and since 2.21 'YYYY' or 'YYYY-MM-DD..YYYY-MM-DD'
  period: string;
  today: string; // since 2.21: the server's day in Europe/Madrid, 'YYYY-MM-DD'
  // since 2.21: the days (Europe/Madrid) of the oldest and the newest movement of the bank
  // window; null when it has none. `window` itself is unchanged
  windowDays: { from: string | null; to: string | null };
  partialReason?: 'window' | 'in_progress'; // since 2.21: of the applied period, never for `all`
  periods: {
    id: string; // 'YYYY-MM', or 'all'
    label: string; // 'Oct 2026'; 'All movements'
    count: number; // movements of the bank window in it
    partial: boolean;
    partialReason?: 'window' | 'in_progress'; // present only when partial
  }[]; // months newest first, then the `all` entry
  unresolvedInPeriod: { count: number; debitCents: number };
};
```

- `period` is `all` (the whole bank window), `current` (the current calendar month in Europe/Madrid by the server clock; the response's `period` is that month's id), since 2.30 `last` (the last full calendar month by the same clock, the month before `current`, December of the year before in January; the response's `period` is that month's id, and everything said of a month holds for it) or a calendar month `YYYY-MM` (since 2.21 also a year or a day range, see "Day ranges and years"). Anything else, or the key repeated, is `400 "Invalid request data."`. A valid month with no movements is a `200` with zero totals and no categories, whether or not it is in `periods`.
- **Transport (since 2.19, IT8b).** On both routes the period is the `period` query parameter or the request header `x-insights-period`: same values, same check, same answer. A bad header value (an empty one and a header sent twice included) is `400 "Invalid request data."` before any bank read; so is the header together with the `period` query parameter, even when they agree, and on `/api/insights/spending` the header together with `from` / `to`. The header exists so that the card can read `GET /api/dashboard` with no query string. Responses are `Cache-Control: no-store`, so no `Vary` is sent; the app has no CORS answer, so the header is for same-origin callers.
- **The card shows the selected period; the Transactions table is not bound to a period** (it lists the whole window). "Category amounts equal the sums of visible rows" ("Totals") therefore holds between the card and the table when the period is `all`; for a month it is guaranteed against that month's movements (the rows of `movements[]` whose `createdAt` is in the month), not against what the table shows.
- **When `period` is absent (no query parameter and no header) the period is `all`**, on both routes, so every caller of 2.16 gets the figures it got. **Since 2.30 the default the customer sees is the last full month** ("Last month"), not the current one: the Overview card's first read of a page load, and of a change of person, asks for `last`, and the month the answer names (`period`, `YYYY-MM`) becomes the chosen period, sent as that month from then on, like a month the customer picked. Before 2.30 the card asked for `current`; "This month" stays a quick choice. The reason is the user's request of 2026-10-06: early in a month the current month is nearly empty, on real data and on the seeds, and the last full month says more. A customer with no spending in the last full month sees the empty state of §8 for that month ("No spending in Sep 2026.", and "See Aug 2026" when the bank's history reaches the month before). The assistant's `get_spending_summary` does not take a period and is unchanged (`SpendingSummary`, whole window or its `from` / `to`).
- A movement belongs to the month of its `createdAt` in Europe/Madrid (the month of the merchant profile, §1). A movement whose date does not parse is in `all` only.
- For a month, `spentCents`, `incomeCents` and `categories[]` (amounts, counts, confirmed and estimated parts) are computed over the movements of that month only, by the rules of "Totals": a category's amount is the sum of that month's rows of that category, and the months' totals add up to those of `all`. Until 2.20 `range` was `{from: null, to: null}` and `partial` was `false` for a month; since 2.21 they describe the applied period (next item), and the month's entry in `periods` says the same as before.
- **Day ranges and years (since 2.21, IT8c).** Two more values, on both routes and both transports:
  - a day range `YYYY-MM-DD..YYYY-MM-DD`, both days included, days in Europe/Madrid. Both must be real calendar dates written with all their digits (`2026-02-30`, `2026-1-1`, three dots, a missing end, a space or any other extra character are invalid) and the first must not be after the second; a single day is `D..D`. There is no maximum span.
  - a calendar year `YYYY` (four digits), in Europe/Madrid.
  - Anything invalid is `400 "Invalid request data."` before any bank read; a valid period with no movements is a `200` with zero totals and no categories. The value is echoed in `period` as given (a range that happens to be a whole month stays a range); `current` still answers its month `YYYY-MM`.
  - A movement belongs to the day of its `createdAt` in Europe/Madrid (so the day changes at 22:00Z in summer time and 23:00Z in winter time). For every period other than `all`, `spentCents`, `incomeCents`, `categories[]` and `unresolvedInPeriod` are computed over the movements whose day is inside the period, by the rules of "Totals": adjacent ranges add up to the range that encloses them, and a year is the sum of its months.
  - `range` is the applied period as days, `{from: 'YYYY-MM-DD', to: 'YYYY-MM-DD'}`, for **every** period other than `all`: a month is its first and last day, a year is 1 January to 31 December. For `all` it is unchanged: `{from: null, to: null}`, or the instants of `from` / `to` when those were sent.
  - `partial` and `partialReason` describe the applied period: `window` when `window.mayBeTruncated` and `range.from <= windowDays.from` (the bank returned a full page and the period reaches the window's oldest day or before it, so older movements of the period, that day's included, may be missing); `in_progress` when `range.to >= today`; `window` wins when both hold; otherwise `partial: false` and no `partialReason`. For a month this equals its entry in `periods`. For `all` nothing changed: `partial` is the one of "Totals" (`false` without `from`), there is no `partialReason`, and its entry in `periods` says whether the window is truncated.
  - `today` is the server's current day in Europe/Madrid, on every answer, so the client computes its presets (this week Monday to Sunday, last week, last month, this year…) against the server clock and sends them as a range, a month or a year. `windowDays.from` / `windowDays.to` are the days of the oldest and newest movement of the bank window (the minimum and maximum worth offering in a date input; a later `to`, such as the Sunday of the current week, is valid).
  - **Limit.** The bank API returns only its most recent movements (`GET /v1/movements`, up to 100, no paging: `docs/contracts.md`), and the app makes no further read. Every period is therefore bounded by that window: one that reaches `windowDays.from` or before it while the window is truncated is `partial` with reason `window`, and one entirely before the window is a `200` with zero totals. When the window is not truncated the bank has nothing older, and a period that starts before `windowDays.from` is complete.
- **Not bound to the period:** `window`, `unresolved` (the review list: sorting a merchant is not tied to a month), `pending` and `periods` are those of the whole bank window, whatever the period. `unresolvedInPeriod` is the period's own part of the review list: `count` movements in review in the period, and `debitCents` the payments among them (the part of the period's `other` amount that is still to review). For `all` it equals the whole list.
- `periods` has one entry per month with at least one movement in the bank window, plus the current month even when it has none, newest first, then `all` (`count` = `window.returned`). `partialReason` is `window` for the oldest listed month when `window.mayBeTruncated` (the bank returned a full page, so the month may have older movements that are not there) and for `all` in that case; `in_progress` for the current month; `window` wins when both hold. A month with neither is `partial: false` and has no `partialReason`.
- The income share shown by the card stays an estimate made by the client from `spentCents` and `incomeCents` of the period; it is not shown when the period's `incomeCents` is 0, nor when the period's `partialReason` is `window`, nor (2.37, #188) for `all`, nor when the period's `partialReason` is `in_progress`.
- With `from` / `to` (no `period`) the answer is the 2.16 one (`unresolved` and `pending` bound to the range) plus `period: 'all'`, `periods` and `unresolvedInPeriod`.
- Proposal rows (`kind` `pending` / `verifying`) have no `category`.

`POST /api/insights/categories`:

- Each movement becomes that category · `confirmed` · source `user` · reason `user`.
- `similar` lists, per non-empty merchant key among them, the **other movements in the current bank answer** with that key and sign that are not already that category and confirmed. Only movements **the customer's rule would decide** count, on both sides: a movement that labelling rules 1–3 decide (an own-account or person transfer known from a counterparty fact, the banks' transfer wording or person wording such as Bizum; an opening row) gives no `similar` entry and no rule when it is among the movements sent, and is never listed or moved as similar to another. Its category is set for that movement only, and no rule is ever keyed by a concept another party wrote. Stored rows of movements the bank no longer returns are never counted or changed.
- With `applyToSimilar: true`: a rule (merchant key → category) is created or replaced for each non-empty key, and the `similar` movements become that category · `confirmed` · source `user_rule`. A later movement of that merchant and sign is `confirmed` · `user_rule` on first read.

`DELETE /api/insights/rules/:merchantKey`: the rule is deleted; movements in the current bank answer whose source is `user_rule` for that key are classified again (rules now, decider in the background); movements set by hand (source `user`) stay. `reclassified` is their count. A movement a decider had already answered gets that answer back in the same call, with no decider request (§1, IT4): creating and deleting a rule costs nothing.

`POST /api/insights/reclassify`: movements in the current bank answer with reason `decider_unavailable` are sent to the decider again. `queued` is the count of those sent. With a decider configured (IT7, 2.22) a movement whose merchant the daily budget left out is not counted: it is stored `decider_budget`, and `queued` counts the movements whose merchant got a new ask in this call; with no decider it is every movement put through the pipeline again. **Cool-down (IT4):** the first retry of a merchant is immediate; once a merchant has been sent more than once in the last 24 hours, a failure younger than one minute is left alone (not counted in `queued`, no decider request), so repeated posts spend one attempt budget per minute at most. Rows with reason `decider_budget` are not this route's: they clear by themselves.

**Audit.** Every category or rule change, from the HTTP routes and from the agent tools, records one event in the existing `events` log: kinds `category.set` (`{channel: 'ui' | 'chat', movementId, from, to, source}`), `rule.created` and `rule.removed` (`{channel, merchantKey, category}`).

**Facts of the routes as merged (SI5, #99; verified by `tests/acceptance/si5-insights-api.test.ts`, `tests/si5-insights-api.test.ts` and the reviewer's probes):**

- **Who and from where.** An operator gets `403 "A customer is required."` on every insights route asked with a method it defines. IT2 (2.12) changed the rest: a method the route does not define is `405 "Method not allowed."` with `Allow`, for anyone and before the session check (it was `403` for an operator, `404` for a customer, `401` without a session), and an `/api/insights/…` path that is no route is `404 "Route not found."` for an operator as for a customer (it was `403` for the operator: the role was checked before the path). The origin rule covers every method that is not `GET` (`POST`, `DELETE`, and a `HEAD` that carries an `Origin`): an `Origin` of another host, of the same host on another port, `null` or unparseable is `403 "Origin not allowed."`; a request with no `Origin` header is accepted. **Rate limit (IT4, replaces "no bucket"):** each of the three write routes (`POST …/categories`, `DELETE …/rules/:merchantKey`, `POST …/reclassify`) takes one token of the `insights` bucket: 30 per minute per customer, refilled continuously, taken after the method, origin and role checks and before the body or the bank is read (a `400` still costs a token; a `405`, an unknown path's `404` and an operator's `403` do not). Over it: `429 {"error":"Too many requests. Wait a moment and try again."}` with `Retry-After` in whole seconds, nothing run and nothing written. `RATE_LIMIT_SCALE` applies as to the other buckets (`0` disables it; the acceptance suites run with `0`). The `GET`s have no bucket.
- **The bank is read first on every write**, and by `GET /api/insights/spending`: `POST …/categories`, `DELETE …/rules/:merchantKey` (also for a key that has no rule) and `POST …/reclassify` answer the bank's error as the dashboard does (`503` / `504`) when that read fails, store nothing and record no event. `GET /api/insights/rules` reads no bank.
- **`POST /api/insights/categories`.** Each id is 1–120 characters; a repeated id counts once. An id outside the bank answer is checked before the sign rule (`404` wins over `400`). `updated` counts the movements actually changed: a movement that is already that category · `confirmed` · source `user` is not written again, so a repeated identical request answers `updated: 0` and records no event. Setting by hand a movement that is `confirmed` · `user_rule` in that same category is a change (its source becomes `user`, one event with `from` equal to `to`), so it then survives the rule's deletion. `similar` has one entry per distinct non-empty merchant key among the movements sent that the customer's rule would decide (2.13: not a transfer or an opening row), also when its `count` is 0, and is computed before the change: with `applyToSimilar: true` it lists the movements the call just moved. A movement the customer had set by hand to another category is "not already that category", so it is listed and, with `applyToSimilar: true`, moved. `rules` lists, of the merchant keys of this call, those that have a rule after it (the whole list is `GET /api/insights/rules`). A movement with an empty merchant key can be set; it has no `similar` entry and never gets a rule (`{updated: 1, similar: [], rules: []}`). A rule that already maps the key to that category is not written again; one that maps it to another category is replaced and becomes the newest.
- **A rule is keyed by merchant key only; the sign rule still applies to each movement it meets.** A movement of the other sign for which the rule's category is not allowed (a credit of a merchant ruled `transfer_person`) is not touched by the rule.
- **`DELETE /api/insights/rules/:merchantKey`.** `{removed: false, reclassified: 0}` (`200`) for a key with no rule, for another customer's key, and for any decodable text that cannot be a key (lower case, too long, an encoded path-traversal shape). A malformed percent escape is the existing `400 "Invalid request path."`, and a further path segment (an unencoded `/`) is `404 "Route not found."`. An empty key is the path `/api/insights/rules`, which has no `DELETE`: `405` since IT2 (2.12; it was `404`). It records one `rule.removed` and no `category.set` for the movements it sends back to the pipeline (their new category is the pipeline's, not the customer's).
- **`POST /api/insights/reclassify`** records no event: it is a retry, not a change.
- **Audit.** `category.set.from` is the movement's previous category id, or `null` when it had none or was still `pending`; `source` is `user` or `user_rule`. A created or replaced rule records `rule.created`. The rows, the rule and their events are written in one transaction; events of channel `ui` have no conversation. Log lines never spell a movement id or a merchant key: the access-log label of the delete is `insights/rules/:key`.
- **`SpendingSummary`.** `range.from` / `range.to` are UTC ISO instants with milliseconds (the inclusive bounds as read), or `null`. `categories[].count` counts every movement that entered the total, refunds included. `confirmedCents` is the confirmed debits minus the confirmed refunds of the category; everything else, movements in `needs_review` included, is `estimatedCents`. `unresolved.totalCents` and a group's `totalCents` are sums of absolute amounts, credits included; a credit in review is listed there and is in no total. A group's `title` is its merchant key, or the description when the key is empty.
- **Rows of `GET /api/movements`.** A merged "Between your accounts" row takes the debit leg's category with `movementIds: [debit, credit]`; one account's view of an internal move lists that leg only. `window`, `X-Movements-Window` and the CSV are unchanged.

`/api/health` and every other response never contain a decider key. `POST /api/actions` is unchanged (the tools below are not accepted there).

## 4. Agent tools (chat only)

| Name | Arguments (strict JSON schema, all required) | Result on success |
|---|---|---|
| `get_spending_summary` | `{from: string \| null, to: string \| null}` (`YYYY-MM-DD`, read as UTC days, or null) | `{status: 'ok', …SpendingSummary}`; each category also has `movements: {ref, id, merchant, amountCents, createdAt, state}[]` (its 5 largest) |
| `list_unresolved_movements` | `{}` | `{status: 'ok', count, totalCents, groups: {merchant, count, totalCents, movementIds, candidates, reason, direction?}[]}` (≤ 10 groups) |

| `set_movement_category` | `{movementId: string, category: CategoryId, applyToSimilar: boolean \| null}` | `{status: 'ok', category, updated, similar: {merchant, count} \| null, ruleCreated: boolean}` |
| `remove_category_rule` | `{merchantKey: string}` | `{status: 'ok', removed: boolean, reclassified: number}` |
| `list_movements` (existing) | `{}` | as today; each movement gains `category: {id, state, reason}` and `ref` |

Failures are `{status: 'failed', error}`:

- a movement id that is not in the actor's current bank answer → `error: 'Movement not found.'`;
- a category the sign rule forbids → `error: 'This category does not fit this movement.'`;
- `set_movement_category` with `applyToSimilar: true` when the newest assistant message of the conversation does not hold an `awaiting.offer` for that merchant key and category → `error: 'Ask the customer first.'`, nothing written;
- `set_movement_category` on a quick-reply click for a movement that is not the stored target → `error: 'This answer is about another movement.'`, nothing written (2.10, see the facts below).

Tools are callable in tests through `runTool(name, args, ctx)` from `src/agent/tools.ts` and are present by name in `toolDefinitions`.

**Merchant text in the insights tools and in the insights digest is the merchant key**, never the raw description.

**Generic keys (IT7, 2.22).** A result row whose merchant is a generic key (§1 "Merchant key": channel words only, such as `CARD PAYMENT`, `RECIBO`, `ADEUDO SEPA`) also has `genericKey: true`; a row with a merchant does not have the field. The rows: each item of `movements` and of `unresolved.groups` in `get_spending_summary`, each group of `list_unresolved_movements`, the result of `suggest_category_choices`, and `similar` of `set_movement_category`. The instructions tell the model to describe such a row as payments with no merchant name, never as a shop or a company. The digest lines carry no such mark.

**Quick replies and their target** (stored on the assistant message by the server, never taken from model text):

| After, in the run | `quickReplies` | `awaiting` |
|---|---|---|
| `set_movement_category` returned `similar` with `ruleCreated: false` | two: the first starts with `Yes`, the second with `No` | `{movementIds, merchantKey, offer: {category}}` |
| `suggest_category_choices` (the last one in the run) | one per candidate (label = English category label), then `Other`, then `Skip` | `{movementIds: [movementId], merchantKey}` |
| a message with an attached movement in `needs_review`, and no category was set in the run | as the row above, for the attached movement | same |
| `get_spending_summary` returned `unresolved.count > 0`, and none of the above; since 2.18 only the first time in a conversation, and not on a turn for which the server chose a product suggestion (plan 24 §4) | two: the first starts with `Review`, the second is `Not now` | none |

On the next turn the model request names the awaited movement ids and merchant key, taken from the newest assistant message's `awaiting`. A click sends the reply's `value` as an ordinary message.

**Cited movements.** `ref` values (`m1`, `m2`, …) are short handles valid within one run. A reply that contains `[m3]` gets that marker removed from the stored text and the movement stored in `extras.citedMovements`; an unknown ref stays in the text.

**Facts of the agent side as merged (SI6a #94, SI6b #102, fix #103; verified by `tests/acceptance/si6-agent-acceptance.test.ts`, `tests/si6b-agent.test.ts` and the reviewer's probes):**

- **Arguments.** Every tool's arguments are strict: a missing or extra field, or a `category` outside the taxonomy ids (eleven since 2.36; the JSON schema offers them as an `enum`), is `{status: 'failed', code: 'invalid_request', error}` and nothing is written. `remove_category_rule` trims and upper-cases its key. `from` after `to` is `failed` with `"The start date is after the end date."`.
- **Order of failures.** A movement id outside the actor's bank answer is `"Movement not found."` before the offer check, the click check and the sign rule, also with `applyToSimilar: true` and no offer (another customer's id and an invented id are indistinguishable). When the bank read fails, every tool is `failed` with the bank's error text; no tool answers zero totals.
- **`get_spending_summary`.** Totals, `window`, `partial`, `pending` and `decider` are those of `GET /api/insights/spending` for the same range. A category also has `labelEs` (Spanish label). An unresolved group's `title` is its merchant key (`''` for a movement with no key), never the description: no insights tool result and no digest line holds a raw description or a transfer concept. `movements` are the movements the category's total is made of, largest absolute amount first.
- **`list_movements`** keeps the raw bank `description`, and for operations the app sent also `fromAccountId`, `toAccountId` and `concept`. The same movement keeps its `ref` within a run; numbering starts at `m1` in every run.
- **`suggest_category_choices`.** `candidates` are the stored ones the sign rule allows. With none stored: the three categories the customer's estimated and confirmed movements use most, then `DECIDER_OPTIONS` order, sign rule applied, never `other`, each `p: null`. A candidate `other` gets no button of its own (it is the `Other` button).
- **`set_movement_category`.** `updated`, `similar` and the rule follow `POST /api/insights/categories` (§3 facts): a movement the customer set by hand to another category is "similar" and a rule moves it. `similar` is `null` when no other movement shares the merchant. One `category.set` per movement changed (so a rule over N similar movements records N of them) and one `rule.created`; `remove_category_rule` records one `rule.removed`. Events of the tools carry channel `chat`, the customer and the conversation.
- **The offer is one-time and belongs to its conversation.** `applyToSimilar: true` needs the newest assistant message of **this** conversation to hold `awaiting.offer` for that merchant key and category. After the rule is created that turn's message holds no offer; an answer to the offer that calls no tool (the customer declined) stores no target at all; an offer in another conversation, for another merchant or for another category does not count; a repeated "yes" is refused. Two requests at once in one conversation: the second is `409`.
- **A click answers the stored target.** When the customer's message is exactly a `value` of the newest assistant message's `quickReplies` and that message has an `awaiting`, `set_movement_category` for a movement outside `awaiting.movementIds` is `{status: 'failed', error: 'This answer is about another movement.'}`, nothing written. Typed words that are not a reply value may name any movement of the customer.
- **`awaiting`.** `movementIds` is the one movement that was suggested, or the one that was set when the message holds an offer. Row 2 of the table is not used for a movement the same run then set. Row 3 needs the attached movement to be in the current bank answer. An answer that called no tool and has no replies of its own keeps the previous target (never its offer, and with no buttons); any other answer without a target closes it.
- **`quickReplies`.** `value` is an opaque string the UI sends unchanged as `content`; labels beyond the prefixes in the table are not frozen. As built: `Yes, apply to the other N` / `No, only this one`; the English category labels, `Other`, `Skip`; `Review them` / `Not now`.
- **`citedMovements`.** At most 8, in order of first mention; every marker of a known ref is removed from the text, also beyond the eighth; `[m1, m2]` works; a ref of an earlier run is unknown. `title` is the activity row's title (bank text): the UI renders it as text.
- **The digest** names the awaited ids and merchant key, the open offer and the conversation's newest attached movement. Its wording, its bounds (five groups) and the number of bank reads per turn are not frozen. A bank read that fails or takes longer than the digest waits only shortens the digest; the turn answers. As merged (IT1 #107): the movements-to-review lines are **not** in every turn's digest. The turn reads the movements for them only for a movement attached to this message, a stored `awaiting`, a stored `needs_review` row of the customer, or a customer with no stored category yet; otherwise the digest says the spending data was not read and states no figure or count, and any spending tool reads the bank itself. The lines always come from that turn's bank answer, never from stored rows. Accounts and contacts are read once per run and shared with the run's view; nothing read from the bank is kept after the run or shared between customers, and a failed read is not kept. A movement to review that reaches the bank after the customer's movements were last classified is therefore first named in the digest on the turn after the next read of the view (Overview or insights route, an attachment, or a tool that reads movements); a tool answer in between already includes it.
- **`POST /api/conversations/:id/messages`.** The body is strict: `content` 1–8000 characters after trimming, `movementId` a string of 1–120; any other key or a bad value is `400 "Invalid request data."`.

## 6. System One wire format

From the official docs ([inputs/research-system-one-api.md](inputs/research-system-one-api.md)). No call was made yet, so the shapes are as documented, not observed.

```text
POST {DECIDER_BASE_URL}/v1/systemone
Authorization: Bearer {DECIDER_API_KEY}
Content-Type: application/json

{ "model": "jev-1.13.0",
  "state": { "description": "<cleaned description>", "direction": "debit",
             "typical_time": "late_night", "typical_day": "weekend",
             "typical_amount": "medium", "occurrences": "few" },
  "questions": {
    "category": {
      "type": "choice",
      "instructions": "<fixed text>",
      "criteria": { "<option id>": "<English description with Spanish and English example words>", … }
    } } }

→ 200 { "model": "jev-1.13.0",
        "answers": { "category": { "type": "choice", "choice": "<option id>",
                                   "confidence": 0.78,
                                   "probabilities": { "<option id>": 0.85, … } } },
        "usage": { "input_tokens": 392, "output_tokens": 65 } }
→ 401 | 422 | 429 (Retry-After) | 529
```

- **One movement per request**, one `choice` question named `category`. No batching of movements.
- `questions` and `answers` are maps keyed by question id. There is no `options` field: the options are the keys of `criteria`, in `DECIDER_OPTIONS` order. The movement text is only in `state`, never in `instructions` or `criteria`. `state` holds exactly the six fields shown: the cleaned description, the direction and the four profile labels. No amount, time, date, id or account.
- `Decision.confidence` is the answer's `confidence`; if absent it is `(p_max − 1/n) / (1 − 1/n)` from `probabilities`. `Decision.model` is the response's `model`. The stored model is `systemone:<that id>`.
- **Reading the answer** (the shape is documented, not observed, so the parser is strict about types and the option set and tolerant about numbers). An error, not retried: no `answers.category` object, a `choice` that is not a string or not one of `DECIDER_OPTIONS`, `probabilities` that is not a map of non-negative numbers, no probability for the `choice`. Accepted and normalised: an option outside `DECIDER_OPTIONS` in `probabilities` is dropped; a sum further than 0.02 from 1 is rescaled to 1; a missing `model` becomes the requested model id; a `confidence` that is absent or not a number from 0 to 1 is computed with the formula above. "Best first" means the provider's `choice` first, then the others by probability; if the `choice` is not the highest probability it still leads, and the confidence is the lower of the answer's and the formula applied to the choice's own probability. The OpenAI decider follows the same rule: a repeated category is dropped, the first candidate stays first, and if another has a higher `p` the confidence is the lower of the reported one and the first candidate's `p`.
- **Log lines** (never a description, a key, a body or the provider's text): `decider_ok {decider, status, ms, inputUnits}`, where `inputUnits` is the answer's `usage.input_tokens` as a number (the field is not named "…tokens" because `log()` redacts such names; SI8 reads it for the cost); `decider_failed {decider, status, retryable, ms}`; `decider_bad_answer {decider, notes}` and `decider_answer_adjusted {decider, notes}`, whose notes name fields and types only; `decider_auth_failed {decider}` once. The 401 latch is per process: a corrected key needs a restart.
- Retryable: 429, 529, any 5xx, 408, timeout, network error. Not retryable: 401, 422, any other 4xx.
- **Attempt budget per item:** at most 3 requests (the first and two retries, waiting `Retry-After` or 0.5 s then 1 s, each wait capped at 5 s). After that, or after a non-retryable error, the item goes to the next decider in the chain, or is stored `decider_unavailable`. After a 401 the decider is not called again by this process.
- At most 8 requests in flight.
- Plain `fetch`; no SDK. The same format is served by gateways under another base URL, which is why the base URL and the model id are settings.

The OpenAI decider has no frozen wire format (it uses the installed SDK): one movement per call, at most 4 in flight, its own client with `maxRetries: 0` and a 15 s timeout, structured output with an enum of `DECIDER_OPTIONS`, `confidence` self-reported. The stored model is `openai:<model>`.

- **"Ask the assistant"** (`category-ask`, and "Resolve in chat"): a new conversation is opened, the movement is attached, the Assistant is shown and one message is sent at once with a body of exactly `{content, movementId}`. `content` is "Why is this {Label}?" for an `estimated` or `confirmed` movement and "Help me categorise this movement." for one in `needs_review` or `pending`. `movementId` is the row's first id (`movementIds[0]`; the first leg of a merged row). While a turn is in flight in another conversation nothing is sent (a second request would be a `409`): the movement waits in the composer and goes with the next message the customer sends.
- **The attachment.** `attached-movement` in `composer-extra` from the click until the POST has succeeded (so during that turn it is in the composer and on the message in flight), with a `button` named "Remove the attached movement"; on a user message (`extras.movement`) it has no button. **A refused or failed send keeps it** (a `404 "Movement not found."`, a bank `503` / `504`, any other error): the error is shown in the page's alert, the text is in the "Not sent. Retry" bubble, and Retry sends text and attachment again. Only the remove button, a successful send or a change of person clears it. (07 said a `404` clears it; the reviewed decision is to keep it.) Titles are bank text and are rendered as text.
- **Quick replies.** A `role="group"` named "Quick replies" of `button`s under the conversation's newest assistant message only (an older message's replies are not rendered, whatever its `extras`). A click sends exactly `{content: value}`: the reply's `value` unchanged, no `movementId`, also when a movement is attached. While any turn is in flight the buttons stay in place and are `disabled` (they are not removed, so nothing shifts); a second click, a double click or a held Enter sends nothing more. A draft typed in the composer is not sent and is kept.
- **Cited movements.** A list named "Movements in this answer" under an assistant message with `extras.citedMovements`, on every such message (not only the newest): title, date, category label, amount.
- **Suggestions** of an empty conversation: the balance question ("What is the balance of my account?" for a one-account customer, else "What are the balances of my accounts?"), "What is the fee of my {main account label}?" (both left out with no account; AS1, the second was a fixed "When is the Aurora account fee waived?"), "I want to speak to a person", then "Where did my money go?".
- **Focus.** After "Ask the assistant", after a reply and after removing the attachment the focus goes to the composer (`textarea` "Message the assistant") on a device with a fine pointer. On a touch device (`pointer: coarse`) the composer is not focused, so the on-screen keyboard does not cover the answer. Every new control is a native `button` or `select` (buttons with `type="button"`) with an accessible name and a visible focus ring; on phones and coarse pointers `category-ask`, "Resolve in chat", the quick replies and the attachment's remove button have a tap area of at least 44 px.
- **After every chat turn the dashboard is read again**, so a category or rule changed in chat is on Overview (chips, card, rules) without a reload.
- **The operator** gets none of these elements on any section.
- **Running the acceptance suite.** On a bank without `demo-` movement ids its live scenarios print `SKIP` lines and it ends with "SKIPPED n of 82 checks": not an acceptance pass. `npm run e2e:demo` (README "End-to-end checks") starts the demo with `DECIDER=none` on fresh data and runs all 82.

## 9. Evaluation harness (SI8)

What `tests/acceptance/si8-heldout.test.ts` may import. Counts, never rates: a rate is `rate(count, rows)`.

```ts
// scripts/eval-score.ts — pure: no file, network, clock or database. Also re-exported
// (parseEvalSet, toMovement, score, EVAL_OWN_ACCOUNTS) from scripts/eval-insights.ts.
export type EvalRow = {
  id: string; description: string; amountCents: number; createdAt: string; concept?: string;
  counterparty: null | 'person' | 'own';
  expected: CategoryId; acceptable: CategoryId[]; difficulty: string;
  adversarial: boolean; injected: CategoryId[]; // the categories an adversarial row's text names
  lang: 'es' | 'en' | 'neutral';
};
export type Outcome = Pick<RowCategory, 'id' | 'state' | 'source' | 'reason' | 'confidence' | 'candidates'>;
export type Tally = { rows: number; strict: number; lenient: number; shown: number; wrongShown: number };
export type Score = {
  total: Tally;
  byDifficulty: Record<string, Tally>;
  byLanguage: Record<string, Tally>;
  adversarial: Tally & { obeyed: number };
  decidedBy: { rules: number; model: number; review: number };
  confusion: Record<string, Record<string, number>>; // expected → got; `review` for a row in review
  reliability: { bucket: string; rows: number; correct: number }[];
  thresholds: ({ threshold: number } & Tally)[];
};
export function parseEvalSet(jsonl: string): EvalRow[]; // both set shapes; throws naming the line and the field, never the text
export function toMovement(row: EvalRow): MovementInput;
export const EVAL_OWN_ACCOUNTS: ReadonlySet<string>; // the `ownAccountIds` that go with toMovement
export function score(rows: EvalRow[], outcomes: ReadonlyMap<string, Outcome>): Score;
export const rate: (count: number, of: number) => number | null;

// scripts/eval-insights.ts — importing it runs nothing.
export type EvalConfig = 'rules' | 'openai' | 'systemone' | `stub:${'oracle' | 'noisy' | 'first-option' | 'failing'}`;
export function evaluate(
  rows: EvalRow[], config: EvalConfig, options?: { profile?: boolean },
): Promise<{ outcomes: Map<string, Outcome>; events: LogEvent[]; threshold: number | null } | { skipped: string }>;
```

- Definitions as in requirements.md "Held-out bars": a row is **shown** when its state is not `needs_review`; `strict` = shown with `expected`; `lenient` = shown with `expected` or an `acceptable` label; `wrongShown` = shown and not lenient (`shown − lenient`). The bars' rates are over the shown rows (`strict / shown`); the report prints each count over the shown rows and over all rows, named by its denominator.
- `adversarial.obeyed` = adversarial rows shown with a category that is wrong even leniently **and** that the row's text names (REQ-HO-2). It is never above `adversarial.wrongShown`.
- `evaluate` calls `classifyMovements` with `wait: true`, one synthetic customer per row and `EVAL_OWN_ACCOUNTS`; `'rules'` is an empty decider chain and needs no key or network. It uses `DATA_DIR` when set (a test calls `setupEnv` first) and a temporary directory otherwise. A configuration whose key is absent resolves to `{skipped}`.
- Command line: `npm run eval:insights -- [--set=dev|heldout|<path>] [--decider=<list>] [--out=<dir>] [--reverse-options] [--no-profile] [--rows] [--price=<USD per million input units>]`. For a path containing `heldout` the output is aggregates only; `--rows` is refused there unless `EVAL_ALLOW_HELDOUT_ROWS=1`; the path is checked as given and as the file it resolves to (a symbolic link is still blind). Exit status: `0` everything asked for was measured; `3` a configuration was skipped for lack of a key or a decider left rows unanswered (the report says `SKIPPED` / `INCOMPLETE`); `2` a wrong option, a missing or empty set, or `--rows` refused; `1` a set that does not parse, or a crash.
